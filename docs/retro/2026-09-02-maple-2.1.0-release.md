# Retrospective: MAPLE 2.1.0

**Date:** 2026-09-02 · **Gate:** G7 · **Reviewer:** Project Reviewer
**Scope:** the full engagement — analysis, ADRs 157–161, documentation, and
the release itself.

## Outcome

2.1.0 is published and verified: on PyPI, on GitHub with assets matching PyPI
byte-for-byte, and installing cleanly into a fresh virtualenv with the new
public surface present and the broker conforming to its contract.

The suite went 1,914 → 2,040 tests, all additions. No test was deleted,
skipped, or weakened. Coverage of `core/result.py` went 68% → 100%. Two
module-level import cycles went to zero.

Six defect classes were closed, each one a control that silently did nothing.
Every one was found by measurement rather than by reading code, and the
measurements are in the ADRs.

## What went well, and why

**Probes beat inspection.** The backpressure defect was invisible in source —
`MessageQueue(max_size=10000)` looks like a bound. It took a stalled-consumer
probe to show 25,000 sends accepted with 15,000 held in an unbounded list. The
same method disproved two of my own hypotheses: I predicted head-of-line
blocking and unbounded key retention, and measurement showed neither. Both are
recorded as *sound* in the hardening analysis rather than quietly dropped.

**Characterization tests before migration.** ADR-160 stated that the scope
migration "is not worth doing without tests that pin default-scope behaviour
first." Ten behavioural tests were written and verified green *before* any
change, and passed unchanged afterwards. When 18 tests then broke, it was
provably the ones asserting on private class attributes — exactly what the ADR
predicted — and not a behaviour regression.

**Blast radius measured before design.** Before keying brokers by URL I checked
whether any test mixed in-memory URLs within a single test. None did. That
turned a risky-sounding change into a bounded one.

**Recording a wrong prediction.** ADR-161 predicted the conformance suite would
find gaps in the implementation that defines it. It found none. The ADR now
says so and explains why — the ADR-159 hardening had already met the standard.

## What went wrong

Three defects reached the release path. All three were mine, and two share a
root cause.

### 1. Reformatting a machine-read file without checking its readers

Normalising `CHANGELOG.md` headings to Keep a Changelog form
(`## [2.1.0] - date`) was a correct improvement that broke **two** parsers:

- `tools/doctrine_lint.py`, which had a dormant version check that the new
  format woke — it then compared the Engineering Doctrine's version against
  MAPLE's product version, two unrelated numbers.
- The release verifier embedded in the workflows, which accepted
  `## 2.1.0 ...` and `## Version 2.1.0 ...` but not the bracketed form. This
  one blocked publication, and only surfaced **after the tag was pushed**.

A `grep -rl CHANGELOG` before reformatting would have found both in seconds.

### 2. Fixing one instance of a duplicated script

The release verifier exists **twice** — in `publish.yml` and again in
`release.yml`. I patched `publish.yml`, saw green tests, and reported it fixed.
The tag push then failed again on the identical error in the copy I had not
looked at, so no GitHub Release was created and 2.1.0 reached PyPI only through
a manual dispatch.

The tests I wrote at the time were part of the problem: they asserted the
behaviour of *a* verifier, not of *every* verifier. The replacement enumerates
the workflows that contain one and asserts each handles the bracketed form.

### 3. Verifying in the wrong environment

The Paperbound documentation page was built to fetch `docs/index.json` and
verified over a local HTTP server. The user opens pages from `file://`, where
browsers block `fetch()` — so it could never have worked for them, and the
fallback notice I added lost the race to the component's own error. Rebuilt to
embed the content, which works in both.

### 4. A drive-by refactor that nearly shipped

Running `black tests/` and `isort tests/` directory-wide reformatted **49 files
with nothing to do with the work** — 2,255 insertions of unrelated churn. It
was caught only by reading `git status` before committing, and reverted.

### 5. Chasing the wrong layer

The documentation page's broken alignment was diagnosed as CSS across two
rounds of plausible-sounding fixes. It was an **unclosed HTML tag**: two code
blocks were missing their opening tags, so an orphan `</div>` closed `<main>`
early and every section after Configuration fell outside it. A tag-balance
check found it in one command and should have been the first thing run, since
"correct until point X, broken from there to the end" is a structural signature,
not a styling one.

## The pattern

Failures 1, 2 and 3 are the same mistake wearing different clothes:

> **I verified the thing I changed, not the things that depend on it.**

The changelog was correct after reformatting — its *readers* were not checked.
The `publish.yml` verifier was correct after patching — its *duplicate* was not
checked. The docs page worked over HTTP — the *user's actual environment* was
not checked.

Every one was a search away.

## Changes adopted

- **Regression tests on the release path.** `tests/test_release_workflows.py`
  now asserts the changelog carries a heading the verifier accepts for the
  current `VERSION`, that every embedded copy handles every heading form, and
  that the caller job grants the permissions the called workflow needs. The
  release path is the one place a mismatch is discovered only after a tag is
  pushed, so it belongs in the suite rather than in a runbook.
- **Contract tests on CI semantics.** `tests/test_ci_workflows.py` pins that
  the summary job cannot report success over a failed job, that the absorbed
  quality checks are still present, and that `F401`/`F811`/`F841` stay
  un-suppressed.
- **Documentation generated, not copied.** The site's reference pages are read
  from `docs/` at build time. Copies drift; the site had been advertising a
  test count two releases stale alongside a 100-line "API reference" against
  the repository's 4,238-line one.

## Working practices to carry forward

1. **Before reformatting any file a program reads, grep for its readers.**
   Changelogs, version files, manifests, lockfiles.
2. **Before declaring a fix complete, grep for other instances of the thing
   fixed.** Duplication is the norm in CI configuration.
3. **Verify in the environment the user actually has**, not the one that is
   convenient to test in.
4. **Run structural checks before styling ones** when a symptom starts at a
   point and continues to the end of a document.
5. **Scope formatters to the files being changed.** Never a whole directory.
6. **Read `git status` before every commit.** It caught the churn in item 4.

## Still open

Recorded here so it is not lost:

- **No metrics export.** A dozen components implement `get_statistics()` and
  none of it leaves the process. The highest-value gap for an operator, and
  more pressing now that `refused` is a number worth alerting on.
- **No drain on shutdown.** In-flight work is discarded on `stop()`.
- **Wall-clock expiry** in `security/link.py` and `error/circuit_breaker.py`;
  `time.monotonic` is used in `autonomy/` and nowhere in the 1.x core.
- **~11 threads per agent**, which caps agents per process.
- **No multi-host transport.** The NATS adapter does not satisfy the broker
  contract; the conformance suite names the five members it lacks. This is the
  natural anchor for 3.0.0.
- **The website source is gitignored.** `website/build_docs_page.py` and the
  narrative pages under `website/docs-src/` exist only in the working tree.
